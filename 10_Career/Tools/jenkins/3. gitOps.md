**GitOps** is a framework and set of best practices that applies the same workflows used for application development (like version control, collaboration, compliance, and CI/CD) to infrastructure automation and deployment.

In a GitOps model, **Git is the single source of truth** for your entire system's desired state. Instead of manually configuring servers or clicking through cloud console UIs to set up environments, you write declarative code that describes exactly what your infrastructure and applications should look like, and you store that code in a Git repository.

Here are the core principles of GitOps:

1. **Declarative Infrastructure:** Your entire system (servers, networking, policies, applications) is defined declaratively as code. You describe _what_ you want the end result to be, rather than writing scripts detailing _how_ to get there.
    
2. **Git is the Single Source of Truth:** All configurations are version-controlled in a Git repository. If it's not in Git, it doesn't exist in the system. This provides an instant, perfect audit trail of every change ever made, who made it, and why.
    
3. **Pull Requests as Operations:** You don't use SSH or manual commands to make changes to a server. Instead, you create a branch, make your changes to the code, and submit a Pull Request. Once the PR is reviewed and merged, the changes are approved to go live.
    
4. **Automated Convergence (Software Agents):** This is the magic of GitOps. Instead of a CI/CD pipeline aggressively pushing changes to your servers, you have a software agent (like ArgoCD or Flux) running _inside_ your environment (usually a Kubernetes cluster). This agent constantly compares the live, actual state of your infrastructure against the desired state defined in the Git repository. If it detects a difference (either because the code changed or because someone manually altered the server), it automatically pulls the new configuration and updates the infrastructure to match Git.
    

### Why use GitOps?

- **Easy Rollbacks:** Since every state your system has ever been in is saved as a Git commit, rolling back a catastrophic failure is as simple as running `git revert`.
    
- **Security:** Developers don't need direct access or credentials to your production servers. They just need access to the Git repository. The automated agents handle the actual deployment.
    
- **Consistency:** It eliminates "configuration drift" (where servers slowly get out of sync with each other over time) because the automated agents constantly force the servers to match the Git repository.
